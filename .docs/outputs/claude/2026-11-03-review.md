# Review of the Remitee escrow planning documents

The challenge PDF (pages 1–4) is the evidence I checked against. Nothing has been implemented, so none of this is verified against running code. The one earlier Claude output, `outputs/claude/2026-11-03-review.md`, is empty, so this is the first substantive Claude review.

## Recommendation

**Adopt the architecture with three simplifications.** Stop planning by Wednesday morning and start coding. Make Monday Nov 9 the submission target and Friday a checkpoint.

The core design is right: one non-upgradeable contract and one Node process (indexer plus API) on SQLite. Most of the excess work is in the indexer's recovery policy and in how detailed the health and API test matrices are. The contract needs nothing extra.

## Prioritized findings

**F1 — Reorg and identity handling has two recovery paths where one would do** (SDD "Reorg recovery" and "Event processing boundary"; spike 002).
- The challenge only asks you to explain your reorg handling in the README, e.g. "wait N confirmations" (p.2).
- The SDD's separate "halt on deployment mismatch" and "rebuild on checkpoint mismatch" policies are avoidable work.
- **Smallest version:**
  - Store the deployment block hash and the hash of the last committed block.
  - Check both at startup and on each scan.
  - On any mismatch, mark the service not ready, wipe the disposable projection and replay from the deployment block.
- This one path still matters locally. A fresh Anvil with the same deployer nonce puts the contract at the same address on chain ID 31337, so chain ID plus address can't detect a stale database. The block hash can.

**F2 — Committing per block, empty blocks included, is more than needed** (SDD "Event processing boundary"; AC7).
- Commit per scanned range instead. Fix `toBlock = head − N`, fetch the logs, then in one SQLite transaction apply the deduplicated journal rows, the projection updates and the cursor/hash for `toBlock`.
- That keeps atomicity and handles empty blocks without a transaction for each one.
- **Use one wake-up mechanism:** a new-block notification or a poll loop that triggers the scan. Not "watcher plus periodic scan." A block-driven loop satisfies "subscribe" (p.2) and never applies callbacks directly.
- Keep the event journal. The challenge says to persist the events (p.2).

**F3 — The API must reuse the contract's deadlines, not recompute them** (SDD "Read model"; spike 003).
- Derive `canCancel`, `canRecover` and `ExpiredRecoverable` from `cancelDeadline` and `expiresAt` as stored from `EscrowCreated`. Use exactly the contract's comparisons: `<` for cancel, confirm and reject; `>=` for recover.
- Recomputing from `createdAt` plus constants risks an off-by-one between contract and API, which is the 20% "logic" criterion.
- Put the derivation in a pure function and spend most API tests on its boundaries. That is cheaper than the HTTP-level matrix in AC9/AC10.

**F4 — Status filtering has to happen in SQL** (SDD "Filter semantics").
- `status=ExpiredRecoverable` means `Pending AND expires_at <= :now`. `status=Pending` means `Pending AND expires_at > :now`.
- Do the filter and pagination in SQL with one captured `now`. Filtering after `LIMIT/OFFSET` silently returns short pages.
- State in the README that `Expired` means only "recovery event indexed."

**F5 — On Anvil, chain time only moves when a block is mined** (spike 003 "Questions to close").
- `evm_increaseTime` alone doesn't change the head timestamp. The demo must mine a block after advancing time so the API can show `ExpiredRecoverable` before anyone calls recover (p.3).
- **Settle staleness as "the most recent RPC poll failed."** Don't use a wall-clock freshness timeout, because an idle Anvil legitimately has an old head timestamp.
- **The two eligibility flags fail differently:**
  - `canRecover` at head time T stays true for the next block, since block timestamps never go backwards.
  - `canCancel` does not: the next block can land past the deadline.
  - Document `canCancel` as best effort.

**F6 — Returning 503 on every RPC failure may be too strict** (SDD "API boundary").
- Returning 503 for all escrow reads when RPC fails makes the read API unavailable whenever the node hiccups.
- Alternative: return recorded state plus `observedChainTime`, `indexedBlock` and `stale: true`, and set eligibility to null while stale.
- 503 only while rebuilding is simpler and easy to defend. This is a candidate decision.

**F7 — State the asset-level fund-locking risk plainly** (p.4: "no way to block or steal funds").
- If a token blacklists the sender (USDC-style), cancel, reject and recover all fail. Only confirm still works. A blacklisted beneficiary is covered by the sender's recovery after 7 days.
- Document this and the pull-payment alternative. Don't build it.
- The SDD already avoids over-promising here (SDD "Contract boundary"; spike 001). Make the scenario explicit for the interview.

**F8 — Small contract-spec gaps** (low effort, protects the 30% security weight):
- Say "custom errors" explicitly in AC3 (the PDF prefers them, p.1).
- Pick whether the getter reverts on an unknown ID or returns a `None` status.
- Index `id`, `sender` and `beneficiary` in the events. Include the actor in the terminal events.
- Treat `token == address(0)` as an explicit check. Don't rely on SafeERC20 behaviour for code-less addresses.

**F9 — README items to call out** (p.1, p.3):
- The challenge explicitly scores documenting ambiguity decisions (p.1). List them:
  - exact boundaries
  - first successful transaction wins
  - beneficiary may not be the escrow contract
  - fee-on-transfer deposits are rejected
- Also explain why each chosen optional was picked (p.3).
- Root `npm install` and curl examples are required (p.4).

**F10 — The planning itself is close to over-investment.** The three spikes are essentially decided already. Fold their conclusions into the SDD now rather than spending another ~90 minutes.

## Accepted strengths

- The scope matches the scoring weights; the 70% on security, logic and tests drives the order of work.
- No owner or upgrade path; terminal state is set before payout (checks-effects-interactions); reentrancy guards on all five mutating entry points, creation included.
- Creation checks the actual received amount (balance delta), with honest token limits.
- The solvency invariant is "balance ≥ pending liabilities," with a donation caveat. That correction of the PDF's equality wording is a good interview point.
- Recorded status and derived eligibility are kept separate, using chain time rather than host time.
- Scope cut rules, a refusal to multiply agent-hours, and JD scope boundaries that are correct (no custody or cross-chain).
