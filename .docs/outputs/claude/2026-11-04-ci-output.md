## Findings (Codex owns the fixes)

**Should fix soon (CI flake risk)**
1. **The PostgreSQL healthcheck can report healthy before PostgreSQL accepts network connections** (`compose.yaml:23`). `pg_isready` without `-h` connects over the local Unix socket. During first-time setup, the postgres image runs a temporary server that only listens on that socket (`listen_addresses=''`). So `up --wait` can return before the real server accepts TCP, and `tools probe` connects over TCP to `postgres:5432`. Every CI run does this first-time setup, so the first probe can fail intermittently. This would be a flaky failure, never a false pass. Fix: `pg_isready -h 127.0.0.1 -p 5432 -U remitee -d remitee`.

**Must check before the docs' data-lifetime claim holds (issue #1)**
2. **Anvil state persistence is claimed but never tested** (`compose.yaml:5-7`, `.docs/local-development.md:69`). I believe the Foundry 1.x image may run as a non-root `foundry` user, but I'm not sure. If it does, a new named volume at `/data` may be owned by root, so `state.json` can't be written. `--silent` would hide those write errors. The result would be a fresh chain after `infra:down` / `infra:up` while PostgreSQL keeps its data: the divergence AC8 has to guard against, happening silently. To check:
   - run `exec anvil sh -c 'id; ls -ld /data; ls -l /data'`;
   - compare the block number across a stop/up cycle.

   Also, Anvil runs as PID 1 without `init`. If it ignores SIGTERM, `infra:down` would take about 20s and lose the final save (at most about 1s of state, given the 1s save interval).

**Low**

3. **`db:sql` honesty** (`scripts/infra.ts:94-103`):
   - `npm run check` and CI never exercise it.
   - It is hardwired to `remitee-local`, so it can't yet prepare the isolated test databases the plan describes.
   - "Atomically" only holds if the file contains no `BEGIN`/`COMMIT`/`ROLLBACK`; psql's docs say `--single-transaction` doesn't work properly otherwise.
   - A `ROLLBACK` inside the file exits 0, which contradicts "returns failure if execution rolls back".
   - Statements that can't run in a transaction (e.g. `CREATE INDEX CONCURRENTLY`) will fail, and psql meta-commands (`\!`, `\i`) do run.

   Either reword the docs or reject transaction-control statements. Don't claim migration coverage in CI.
4. **Original error can be lost** (`scripts/infra.ts:61-67`). If `clean()` in `finally` throws, or the logs call in `catch` times out, that error replaces the original test failure. The exit code stays 1, so it's never a false pass, but the real cause is lost.
5. **Local check runs leave image tags behind.** Each local `npm run check` builds a `remitee-check-*-tools` image, and `down` without `--rmi local` never removes it. The layers are shared, so disk cost is small, but tags pile up. I kept CI to the contract's exact command; runners are discarded after each job anyway.
6. **Negative and lock tests prove less than they suggest:**
   - The stopped-DB test exercises a failed lookup of the service name, not a refused or hung connection. That's enough here; the health work in #5 should cover the timeout path.
   - The comment at `smoke.ts:46` mentions schemas, but the test only shows two sessions in one database contending. The docs' "database-local, not schema-local" statement is correct PostgreSQL behaviour but isn't proven by this test.

   I found no false-positive negative tests: the stopped-DB check requires exit code exactly 1 plus both markers, and probes pass before and after it.
7. **Naming and diagnostics:**
   - `infra:down` runs `compose stop`, which differs from Docker's meaning of `down`. The docs describe it accurately.
   - `--silent` makes the failure logs in `test()` useless for Anvil.
